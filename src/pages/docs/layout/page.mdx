    <Section title="Overview">
        `Page` holds route-level content. It renders a single `div` that applies 32px of
        vertical spacing between its direct children, increasing to 48px from the `md`
        breakpoint, and optionally renders a `PageHeader` when a `title` or `subtitle` is
        supplied.

        `Page` is deliberately minimal. **The parent layout owns the `main` landmark, the
        container width, and the window padding.** This keeps `Page` reusable inside any
        shell, whether that shell has a sidebar, a navbar, or neither.
    </Section>

    <Section title="Layout Contract">
        ### Responsibilities
        Understanding the split makes it clear where each class belongs:

        | Concern | Owner |
        | --- | --- |
        | `main` landmark | Parent layout |
        | Container width (`max-w-container`, `mx-auto`) | Parent layout |
        | Window padding (`px-6 lg:px-8`, `py-8 md:py-12`) | Parent layout |
        | Breadcrumb placement and spacing | Parent layout |
        | Spacing between page-level blocks | `Page` |
        | Page heading and page-level actions | `Page` / `PageHeader` |

        ### Parent Layout Example
        A typical route shell wraps `Page` with the landmark, container, and padding:

        ```tsx
        <main className="w-full grow max-w-container mx-auto px-6 lg:px-8 py-8 md:py-12">
          <Page title="Inventory Dashboard" subtitle="Live taproom and warehouse inventory.">
            {/* Page content */}
          </Page>
        </main>
        ```

        Because `Page` renders a plain `div`, it can also sit beside other page-level
        blocks such as a breadcrumb trail without fighting over spacing.
    </Section>

    <Section title="Page">
        ### Description
        A route-level wrapper that applies consistent vertical rhythm to its direct children
        and optionally renders a `PageHeader`.

        The header is rendered when either `title` or `subtitle` is provided. When both are
        omitted, `Page` renders only its children, which lets you pass a fully custom
        `PageHeader` as the first child instead.

        ### Props
        The `Page` component accepts the following props:

        | Prop | Type | Default | Description |
        | --- | --- | --- | --- |
        | title | string | - | Page title; renders a `PageHeader` when provided |
        | subtitle | string | - | Page subtitle; also renders a `PageHeader` when provided |
        | className | string | - | Additional class names for the root `div`, which includes the header |
        | children | ReactNode | - | Page content |

        The component also accepts all standard HTML `div` attributes, which are applied to
        the root element.

        > **Note:** `className` applies to the root element, so utilities such as
        > `max-w-prose` or custom spacing affect the header as well as the content.
    </Section>

    <Section title="Spacing Scale">
        ### Vertical Rhythm
        `Page` is the anchor of the spacing scale. Every value below is expressed in the
        utilities that produce it:

        | Scope | Mobile | `md` and up | Owner |
        | --- | --- | --- | --- |
        | Window padding | 32px (`py-8`) | 48px (`md:py-12`) | Parent layout |
        | Page-level blocks | 32px (`space-y-8`) | 48px (`md:space-y-12`) | `Page` |
        | Breadcrumb to content | 24px (`space-y-6`) | 32px (`md:space-y-8`) | Parent layout |
        | Section internal gap | 32px (`space-y-8`) | 32px (`space-y-8`) | `Section` |
        | Nested heading to content | 16px (`space-y-4`) | 16px (`space-y-4`) | Author |

        ### Heading Scale
        Headings use a single bold weight so size alone carries the hierarchy:

        | Component | Size |
        | --- | --- |
        | `Heading1` | 36px |
        | `Heading2` | 30px |
        | `Heading3` | 24px |
        | `Heading4` | 20px |
        | `Heading5` | 18px |

        The example below shows the scale in practice: major areas separate at the page
        level, sections keep 32px internally, and nested headings stay 16px from their body
        content.
    </Section>

    <Section title="PageHeader">
        ### Description
        A header for page titles, with optional actions that align to the right from the
        `md` breakpoint.

        When `title` or `subtitle` is provided, `PageHeader` renders a `Heading1` and places
        any children in an actions group. When both are omitted, the children render
        directly, which allows a fully custom header while keeping the semantic `header`
        element and the responsive layout.
    </Section>

    <Section>
        ### Props
        The `PageHeader` component accepts the following props:

        | Prop | Type | Default | Description |
        | --- | --- | --- | --- |
        | title | string | - | Header title text, rendered as a `Heading1` |
        | subtitle | string | - | Subtitle text, rendered beneath the title |
        | className | string | - | Additional class names forwarded to the `Heading1` |
        | wrapperClassName | string | - | Additional class names for the `header` element |
        | children | ReactNode | - | Actions when `title` or `subtitle` is set; otherwise the full header content |

        The component also accepts all standard HTML `header` attributes.

        ### Responsive Layout
        - **Mobile:** the title block and actions stack vertically
        - **`md` and up:** `md:flex md:items-start md:justify-between` places the title on the left and actions on the right, aligned to the top of the title
    </Section>

        ### Page with Header Actions
        Pass a `PageHeader` as the first child of `Page` when the header needs actions.
        Use the `title` and `subtitle` props on `Page` only when no actions are required.
    </Section>

    <Section title="Accessibility">
        The Page components follow semantic HTML and accessibility best practices:

        - `PageHeader` renders a semantic `header` element
        - Page titles render as a single `h1`, preserving heading hierarchy
        - `Page` itself renders a neutral `div`, so the parent layout can own exactly one `main` landmark per route

        When implementing pages, ensure that:

        1. Exactly one `main` landmark wraps the page content
        2. Page titles are descriptive and provide clear context
        3. Content is organized logically within `Section` components
        4. Interactive elements have visible focus states
        5. Content remains readable and navigable at all screen sizes
    </Section>

    <Section title="Best Practices">
        ### Page Structure
        - Let the parent layout own the `main` landmark, container width, and window padding
        - Use the `title` and `subtitle` props for simple headings
        - Pass a `PageHeader` as the first child when the header needs actions or custom content
        - Organize content with `Section` components so the 32px internal rhythm is consistent

        ### Content Organization
        - Treat each direct child of `Page` as a major block; the 32px to 48px gap is intentionally large
        - Keep nested headings 16px from their body content so groups read as units
        - Constrain narrow content with a wrapper rather than with `className` on `Page`

        ### Layout Patterns
        - Place breadcrumbs in the parent layout above `Page`, using 24px to 32px spacing
        - Reuse the same layout shell across routes for predictable page chrome
        - Reach for `wrapperClassName` on `PageHeader` before replacing the component
    </Section>
